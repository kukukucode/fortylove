# Supabase SQLの使い分け

## 既存の本番Supabaseを更新する

1. SQL Editorで`inspect_current.sql`をファイル全体のまま実行し、1つの結果表を保存する。この処理は読み取り専用である。
2. Supabase Dashboardでバックアップを確認する。
3. 棚卸し結果の先頭が`SUMMARY / READY`であることを確認してから、`manual/production_upgrade_20260905.sql`をファイル全体のまま実行する。`UPGRADE_TARGET / MISSING`は統合アップグレードで追加されるため、実行前には存在していなくても問題ない。
4. 続けて`verify_production.sql`を実行する。
5. 最初の確認結果がすべて`true`、重複パスの結果が0件、適用バージョンが1件であることを確認する。

統合アップグレードはトランザクション内で実行されます。途中で前提不足や重複データを検出した場合は全体をロールバックし、利用者・イベント・予約・既存カラムを削除しません。

GitにあるSQLとSupabaseの実DBは自動同期されません。GitHubやVercelへのpushだけではDBは変わらず、SQL EditorやSupabase CLIで適用した時点で初めて変更されます。したがって、実DBの棚卸し結果を正として判断します。

## 空のSupabaseを新規構築する

SQL Editorで`schema.sql`を実行します。これは現行構造の完成版スナップショットです。既存の本番環境へ繰り返し実行するファイルではありません。初期管理者が必要な場合だけ、内容を変更した`seed.sql`を続けて実行します。

## 今後の変更

本番DBを変更するときは、[データベース変更手順](../docs/operations/database.md)を確認してください。

- `migrations/`へ日付順の新規ファイルとして追加する。
- 一度適用したマイグレーションは編集しない。
- テーブル・関数・制約の変更と、必要な権限設定を同じマイグレーションに含める。
- `schema.sql`は新規環境用の完成形として同期する。
- `tests/`へ回帰テストを追加し、GitHub Actionsでスキーマと統合SQLを検証する。

貼り付け元の統合セットアップSQLに含まれていた、重複管理者の自動削除、旧カラムの`drop ... cascade`、イベント区分の一括更新は、既存データを意図せず変更するため統合アップグレードには含めていません。
