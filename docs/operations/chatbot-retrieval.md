# チャットBotの原本管理・検索更新

## 反映の順序

1. DBバックアップを確認し、既存の未適用SQLを先に適用する。
2. `supabase/migrations/20261102_chatbot_retrieval_versions.sql` を全体で実行する。
3. 新しいアプリを反映する。新コードはこのマイグレーションがない場合、資料検索・取り込みをエラーにして保護する。
4. super_adminでMarkdownを選択し、解析結果・変更行を確認して反映する。対象ごとの参照元設定は従来どおり維持される。
5. 同じ資料を再アップロードし、版が増えること、履歴から旧版を復元できること、一般会員が原本APIへアクセスできないことを確認する。

本番の既存データを消すSQLは含めていない。古いマイグレーションを修正・再適用する必要はない。アプリ更新中はMarkdownの編集を控える。旧アプリへ戻す場合も、原本と検索データを別々に更新しないよう取り込みを止める。

## 原本と公開範囲

- `chatbot_documents` のUUIDが文書の識別子。同名ファイルは同じ文書の新しい版となり、別名ファイルは別文書になる。
- `chatbot_document_versions` にMarkdown原文・SHA-256・モデル名・版番号・登録者・日時・検索用スナップショットを保存する。
- 原本は公開ディレクトリやGitに置かない。RLS有効・匿名/一般認証ロールの権限なし。原本の閲覧・復元APIはその時点でDB上のsuper_admin権限を確認する。
- service_roleは原本テーブルの読み取りのみ。更新は権限確認付きRPCへ集約する。アプリの独自認証をSupabase Authへ移行する変更は含めない。
- Private Storageの代わりに非公開DBテーブルを使い、原本の保存・検索データ差し替え・有効版の変更を同じトランザクションにする。
- 今回より前の原本は存在しないため捏造しない。既存検索データは使えるが、原本の履歴は再取り込み後からとなる。
- 復元は過去版を書き換えず新しい版として記録する。確認時から版が変わっていた場合は拒否する。削除操作は原本・全版・検索データ・参照元設定を一括削除するため、削除前に必要な原本をダウンロードする。
- 最大10ファイル・合計1,000,000バイト・1ファイル1,000件。解析はサーバー側。変更表示は追加/削除各100行までで、完全な行単位diffではない。元ファイルは手元で編集して再取り込みする。

## 回答の決め方

1. イベントの日時・場所・空席はDBから取得する。日付・名前・種類を絞り、該当なしを別イベントで埋めない。複数候補や解釈できない条件は利用者へ確認する。
2. それ以外は許可されたMarkdownと公開FAQだけから、キーワード上位20件・意味検索上位20件をDBで取り出す。意味検索API障害時はキーワード検索を継続する。
3. 独立した二つの順位をRRFで統合する。同じ正規化タイトルの公開FAQをMarkdownより優先し、同種の候補は更新日時を比較する。非アクティブな項目を除外する。
4. 完全一致した質問/見出し、利用者が選択した候補は直接回答する。それ以外は候補提示か根拠に限定したGemini生成へ回す。類似度だけで回答確定しない。
5. 一般回答は明示した同意ボタンからのみ実行し、公式情報と区別する。

直近4件までの利用者の質問を、代名詞などの追加質問の検索文脈に使う。Botの回答を事実の根拠として再送しない。履歴は権限に使用せず、検索対象は毎回サーバーで決める。super_adminの対象切り替え時も会話を分離する。

出典には取得した文書ID・版・節を保持し、プレビューでは資料名・版・節を表示する。異なる見出しで矛盾する文章を自動で完全に検出するものではない。会費や参加条件などの正本は運用上も揃えること。

## 検証と測定

- `lib/chatbot-retrieval.test.ts`: 根拠付き回帰質問、誤った直接回答の抑止、FAQ優先、RRF、文脈、イベント条件。
- `supabase/tests/chatbot_retrieval_versions.sql`: 実DBで原子保存・復元・競合拒否・非公開/無効データ除外・1,000件で取得上限40件。CIの既存databaseジョブで実行する。
- `e2e/experience.spec.ts`: PC/スマホで変更確認後の反映、失敗表示、対象別の文脈引き継ぎ。
- `scripts/quality/chatbot-retrieval-benchmark.mjs`: `PGHOST=127.0.0.1`、`PGDATABASE=fortylove_chatbot_test` の隔離DB（schema適用済み）でのみ動作する。合成資料1,000件、ウォームアップ後20回のDB p95と転送サイズを `.ops-reports/chatbot-retrieval.json` に出力する。全データはロールバックする。

DB内の順位計算は現在全候補を走査するため、インデックスを使った近似近傍検索ではない。改善するのはアプリへの全件転送とアプリ側処理。大規模化時は実測を見てpgvector等への移行を検討する。

ローカル測定は本番の応答速度や回答精度を保証しない。実資料の正解根拠付き質問で、回答可否・誤回答・p95・Embedding/生成API使用量を反映前後に比較する。無料枠や外部APIの遅延・料金は固定値を仮定しない。
