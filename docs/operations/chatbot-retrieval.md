# チャットBotの原本管理・検索更新

## 反映の順序

1. DBバックアップを確認し、既存の未適用SQLを先に適用する。
2. `supabase/migrations/20261102_chatbot_retrieval_versions.sql` を全体で実行する。
3. 新しいアプリを反映する。新コードはこのマイグレーションがない場合、資料検索・取り込みをエラーにして保護する。
4. super_adminでMarkdownを選択し、解析結果・変更行を確認して反映する。対象ごとの参照元設定は従来どおり維持される。
5. 同じ資料を再アップロードし、版が増えること、履歴から旧版を復元できること、一般会員が原本APIへアクセスできないことを確認する。

本番の既存データを消すSQLは含めていない。古いマイグレーションを修正・再適用する必要はない。アプリ更新中はMarkdownの編集を控える。旧アプリへ戻す場合も、原本と検索データを別々に更新しないよう取り込みを止める。

## 原本と公開範囲

- `chatbot_documents` のUUIDが文書の識別子。同名ファイルは同じ文書の新しい版となり、別名ファイルは別文書になる。
- `chatbot_document_versions` にMarkdown原文・SHA-256・モデル名・版番号・登録者・日時・検索用スナップショットを保存する。
- 原本は公開ディレクトリやGitに置かない。RLS有効・匿名/一般認証ロールの権限なし。原本の閲覧・復元APIはその時点でDB上のsuper_admin権限を確認する。
- service_roleは原本テーブルの読み取りのみ。更新は権限確認付きRPCへ集約する。アプリの独自認証をSupabase Authへ移行する変更は含めない。
- Private Storageの代わりに非公開DBテーブルを使い、原本の保存・検索データ差し替え・有効版の変更を同じトランザクションにする。
- 今回より前の原本は存在しないため捏造しない。既存検索データは使えるが、原本の履歴は再取り込み後からとなる。
- 復元は過去版を書き換えず新しい版として記録する。確認時から版が変わっていた場合は拒否する。削除操作は原本・全版・検索データ・参照元設定を一括削除するため、削除前に必要な原本をダウンロードする。
- 最大10ファイル・合計1,000,000バイト・1ファイル1,000件。解析はサーバー側。変更表示は追加/削除各100行までで、完全な行単位diffではない。元ファイルは手元で編集して再取り込みする。

## 回答の決め方

1. イベントの日時・場所・空席はDBから取得する。日付・名前・種類を絞り、該当なしを別イベントで埋めない。複数候補や解釈できない条件は利用者へ確認する。
2. それ以外は許可されたMarkdownと公開FAQだけから、キーワード上位20件・意味検索上位20件をDBで取り出す。意味検索API障害時はキーワード検索を継続する。
3. 独立した二つの順位をRRFで統合する。同じ正規化タイトルの公開FAQをMarkdownより優先し、同種の候補は更新日時を比較する。非アクティブな項目を除外する。
4. 見出しに完全一致する質問、具体的なキーワードで一意に引けた質問、利用者が選んだ候補には本文を返す。「入会金／入会費」「借りる／貸し出し」などの言い換えは字句検索で揃える。それ以外の関連資料は上位3件までを使い、Geminiで回答をまとめる。回答を生成できなければ、質問の具体的な語句に一致する候補を選択肢にする。
5. 資料をもとに回答できない場合、ボールの素材やテニスのルールなどの一般的な質問には「一般的な回答を見る」を表示する。ボタンを押したときに質問文をGeminiに送り、公式情報と区別して表示する。

直近4件までの利用者の質問を、代名詞などの追加質問の検索文脈に使う。Botの回答を事実の根拠として再送しない。履歴は権限に使用せず、検索対象は毎回サーバーで決める。super_adminの対象切り替え時も会話を分離する。

回答APIは出典情報として取得した文書ID・版・節を返す。異なる見出しで矛盾する文章を自動で完全に検出するものではない。会費や参加条件などの正本は運用上も揃えること。

- `e2e/experience.spec.ts`: PC/スマホで変更確認後の反映、失敗表示、対象別の文脈引き継ぎ。
- `scripts/quality/chatbot-retrieval-benchmark.mjs`: `PGHOST=127.0.0.1`、`PGDATABASE=fortylove_chatbot_test` の隔離DB（schemaと下記のインデックス用マイグレーション適用済み）でのみ動作する。件数は引数で200・1,000・5,000・10,000から指定でき、省略時は1,000件。旧方式と新方式をそれぞれウォームアップ後に15回実行し、DB実行時間・転送量・候補の比較用ハッシュとRecall@20を `.ops-reports/chatbot-retrieval.json` に出力する。Recall@20は、全件を比較して求めた意味検索上位20件を、新方式でも何件取得できたかを表す。合成データはロールバックする。

### インデックス付き検索（2026-11-25）

`20261123_optimize_chatbot_search.sql` まで適用したDBに `20261125_index_chatbot_retrieval.sql` を実行する。pgvector 0.8.0以上が必要。既存の埋め込みから索引を作るため、資料の再取り込みやGeminiの再呼び出しは不要。生成列の追加とインデックス作成で対象2テーブルをロックするので、利用が少ない時間に適用する。ロックを3秒以内に取得できない場合はトランザクションを中止する。アプリを先に更新した場合は新RPCが見つかるまで従来のRPCを利用する。

字句検索では事前計算したbigramをGINインデックスで絞り込み、意味検索ではpgvectorのHNSWで候補を取得する。参照元の絞り込みでMarkdown候補が足りない場合は、許可済みの資料だけで厳密検索を補う。直接回答で終わらない質問は字句・意味の2回に分かれるが、意味検索では字句スコアを再計算しない。両方の順位を統合した後、複数の話題がある場合はそれぞれの根拠が上位に入るよう並べる。

同じ隔離PostgreSQL 18.6、pgvector 0.8.1での合成データ測定。単位はms、各15回の中央値。

| Markdown件数 | 旧字句 | 旧ベクトル付き | 新字句 | 新意味 | Recall@20 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 77.9 | 166.0 | 4.2 | 2.9 | 100% |
| 10,000 | 1,151.9 | 2,084.1 | 56.0 | 34.9 | 100% |

この測定にはネットワーク、Gemini、実資料の回答精度は含まない。CIでは公開範囲、FAQ編集後の検索、字句結果の互換性、複数話題の根拠選出を検証する。

### DB内の検索最適化（2026-11-23）

`20261102_chatbot_retrieval_versions.sql` を適用済みのDBには、`20261123_optimize_chatbot_search.sql` だけを適用する。PostgreSQLが正規化済みテキスト・キーワードと埋め込みのノルムを既存行から生成し、その後の書き込みでも更新する。適用時は対象2テーブルの書き換えと排他ロックが発生するため、データ量を確認して利用の少ない時間に実施する。

検索時は候補IDとスコアで上位を選び、元の本文や出典は返却候補に限って読み込む。RPCの引数・返却形式・スコア閾値は同じため、アプリの更新と同時に適用する必要はない。既存資料の再取り込みや再埋め込みも不要。CIでは `supabase/tests/chatbot_search_optimization.sql` で、各20件の候補選出、公開範囲、本文と検索用データの同期を検証する。

この時点の順位計算は対象範囲を全件走査していた。

同一マシンの PostgreSQL 17.6 で、変更前後に同じ合成データを投入した比較。単位はms、各15回の中央値。

| Markdown件数 | 字句検索（変更前 → 変更後） | ベクトル付き（変更前 → 変更後） |
| ---: | ---: | ---: |
| 200 | 51.4 → 6.6 | 85.1 → 23.4 |
| 1,000 | 183.1 → 31.2 | 608.5 → 207.9 |
| 5,000 | 855.8 → 241.7 | 2,673.7 → 1,102.8 |
| 10,000 | 2,203.1 → 466.4 | 4,485.7 → 2,582.3 |

全条件で候補・返却内容・小数12桁までのスコアが一致した。比較には、字句と意味検索の両方で上位20件が埋まる合成データを使用した。

ローカル測定は本番の応答速度や回答精度を保証しない。実資料の正解根拠付き質問で、回答可否・誤回答・p95・Embedding/生成API使用量を反映前後に比較する。無料枠や外部APIの遅延・料金は固定値を仮定しない。
